# 开发规范

## 1. 命名规范

| 类型 | 规范 | 示例 |
| --- | --- | --- |
| 包名 | 全小写，域名倒序 | `com.ifinance.aicustomer` |
| 类名 | UpperCamelCase | `ChatServiceImpl` |
| 方法名 | lowerCamelCase | `getHistory` |
| 常量 | 全大写下划线 | `DEFAULT_SYSTEM_PROMPT` |
| 接口 | 动词或领域名 | `ChatService` |
| 实现类 | 接口名 + Impl | `ChatServiceImpl` |
| 测试类 | 被测类名 + Test | `ChatControllerTest` |
| 表名 | 小写下划线 | `chat_message` |
| 字段 | 小写下划线 | `session_id` |

## 2. 分层规范

- Controller 不写业务逻辑，只做参数绑定、校验与响应封装。
- Service 只依赖接口与 DTO，不依赖 Repository 之外的实现细节。
- Repository 不写 SQL 之外的业务判断。
- Entity 不允许直接作为接口出参。

## 3. 提交规范

建议使用 Conventional Commits：

```text
feat: 新增智能客服对话接口
fix: 修复历史记录排序问题
docs: 补充 Nacos 配置说明
test: 增加服务层单元测试
```

## 4. 代码评审检查项

- 是否存在未处理的异常或吞异常。
- 是否将敏感信息写入日志或提交到仓库。
- 数据库查询是否命中索引。
- 是否缺少参数校验。
- 是否在正确分层中实现逻辑。
- 新增公共能力是否补充测试。

## 5. 注释规范

- 公共类、接口、核心业务方法必须编写 Javadoc，说明方法职责、参数与返回值。
- Controller、Service、AOP 切面、Tool 等关键节点必须注释清楚调用时机。
- 注释描述“做什么”和“为什么”，不写“给变量赋值”这类废话注释。
- 修改逻辑时必须同步更新相关注释，禁止注释与代码不一致。

## 6. 日志规范

- 关键链路使用 INFO：收到请求、AI 调用完成、消息落库、模型初始化。
- 排查类信息使用 DEBUG：历史上下文查询、Tool 调用、消息条数。
- 异常使用 WARN/ERROR，并输出异常堆栈。
- 日志必须使用占位符 `{}`，禁止字符串拼接。
- 禁止打印完整对话内容、API Key 等敏感信息，使用 sessionId、消息长度、modelName 代替。

## 7. 工具规范

- 使用 `.editorconfig` 统一缩进与换行。
- Java 文件使用 4 空格缩进，YAML/XML 使用 2 空格缩进。
- 文件编码统一 UTF-8。
